## Part I — System Architecture Specification (5-Plane LLM-First Multi-Agent Topology & VPC-SC)

## 1. Architectural Vision, Design Tenets & Customer Environment Template Manifest

Analyzing an enterprise's Post-Quantum Cryptography (PQC) posture requires simultaneous mastery of cloud control-plane telemetry, quantum cryptanalysis literature, application wire-protocol constraints, and business-impact context. An LLM without evidence tools would hallucinate inventory and arithmetic, whereas a purely static scanner cannot reason about which applications depend on each key or design a consultative migration architecture. The Agentic PQC Readiness & CBOM Engine solves this with an LLM-first multi-agent architecture in which Gemini agents do all of the reasoning over read-only evidence and auditable calculations:

- Tenet 1 — LLM-First Separation of Concerns (Gemini Reasoning vs. Evidence & Auditable Arithmetic): A Gemini coordinator agent built with Google ADK converses with the user and delegates to five Gemini specialist agents (discovery, correlation analysis, quantum risk, remediation architecture and report writing), which perform all correlation, prioritization, recommendations and narrative. Python tools only collect read-only evidence from Google Cloud APIs or compute auditable numbers (scorecard ratios with numerators and denominators, Mosca arithmetic, literature-based qubit estimates with citations); they never correlate, prioritize or recommend.
- Tenet 2 — 100% Agentless, Zero-Plaintext Control-Plane Introspection: The system operates exclusively via read-only Google Cloud control-plane APIs. It never installs host agents, never inspects data-plane network packets, never reads Secret Manager payloads, and never accesses private cryptographic key material.
- Tenet 3 — Stakeholder-Calibrated Mosca Parameters: Mosca values (X data shelf-life, Y migration time, Z threat horizon) stated by stakeholders in interviews, in the Agentic PQC Discovery Questionnaire or in uploaded documents (detailed in Part III of this Guide) are recorded by calibrate_assessment_context in a scope-keyed calibration ledger (tools/calibration_engine.py). get_historical_calibration_profile returns only the calibration recorded for the requested scope; values not provided come from a clearly labeled sector baseline and are reported as not calibrated.
- Tenet 4 — Portable Customer-Environment Template Design: Every runtime URI, project identifier, storage bucket, and IAM principal is parameterized via environment variables so the architecture can be deployed identically in a customer's single-tenant production enclave, a multi-tenant regional @google.com consulting hub (NorthAm, EMEA, India, APAC, LATAM), a central governance hub, or a consultant's workstation.

## 2. Five-Plane System Architecture & End-to-End Data Flow (C4 Container & Component View)

The platform is architected across five decoupled horizontal planes that turn read-only evidence from Google Cloud control-plane APIs into evidence-based findings, an auditable scorecard, per-key migration runbooks and reports written by Gemini agents:

1. Plane 1 — Multi-Channel Presentation, Multi-Tenant Auth & API Layer (pqc_agent/workspace_server.py, pqc_agent/auth_guard.py, main.py): FastAPI server built on the ADK FastAPI app, protected by Cloud Run Native Identity-Aware Proxy (--iap --no-allow-unauthenticated) with direct Google Sign-In redirect (accounts.google.com), signed X-Goog-IAP-JWT-Assertion verification and OAuth 2.0 Authorization Code + PKCE (S256) delegation across global regions (NorthAm, EMEA, India, APAC, LATAM), exposing (a) the Agentic PQC Workspace Portal (GET /) with a verified Gemini model selector, P1-P5 phase shortcuts (each opens a new chat), multimodal file upload, per-user persistent conversation history, tool-call traces and "Answered by" telemetry per answer, (b) authenticated REST endpoints /api/chat (returns HTTP 502 with an explicit error when the model fails; no templated fallback), /api/models, /api/sessions, /api/health, /api/connection, /api/gcloud and /api/auth/*, (c) the native Google ADK Developer UI (/dev-ui/, local-only), (d) an optional Vertex AI Agent Engine deployment (python main.py deploy), and (e) a CLI (python main.py ask | tools | cbom) for scripted runs.
2. Plane 2 — Multi-Agent Orchestration & Grounding Plane (pqc_agent/agent.py): Built with Google ADK (Agent Development Kit) on Gemini (Vertex AI). A coordinator agent converses with the user, answers follow-ups directly and delegates to five Gemini specialist agents exposed as AgentTools: discovery_agent (facts-only inventory of Cloud KMS keys, TLS policies and target proxies, KMS import jobs, certificates and private CAs; no prioritization), correlation_analyst_agent (which workloads depend on which keys, with exactly one evidence level per link, and the application impact of migrating each key), quantum_risk_agent (auditable scorecard, Mosca with recorded or labeled default parameters, cited quantum resource estimates, the illustrative CRQC scenario model and risk prioritization with explicit reasoning; no financial figures), remediation_architect_agent (per vulnerable key: target PQC algorithm and justification, gcloud commands with the HSM protection level preferred for production, IAM binding, application change, validation, rollback and decommissioning steps, sequenced in phases; proposed names marked as proposed) and report_writer_agent (executive and technical reports written only from the findings passed to it, plus the CycloneDX CBOM). Every agent uses the Gemini model and thinking level selected in the portal (default Gemini 3.1 Pro (custom tools), thinking level MEDIUM). Mandatory grounding rules: never invent resources, numbers or citations; separate facts from labeled inferences; carry the correlation evidence level; use scorecard numbers exactly as computed with numerator and denominator; report tool errors explicitly; label demo data; never pass internal Vertex AI tenant (-tp) projects as scope; and a standardized 6-section consultative deliverable layout.
3. Plane 3 — Evidence-Collection & Auditable-Calculation Tool Plane (tools/): Read-only tools invoked by the specialist agents; they never correlate, prioritize or recommend: (3A) Cloud KMS inventory, workload evidence, crypto-asset discovery, scorecard and CBOM export (tools/gcp_inventory.py), (3B) TLS policy / target proxy and BYOK import-job collectors (tools/pqc_detectors.py), (3C) literature-based quantum resource estimates with citations plus an illustrative CRQC scenario model (tools/quantum_engine.py), (3D) Mosca calibration ledger and uploaded-artifact reader (tools/calibration_engine.py), (3E) report saver for agent-written Markdown and HTML (tools/report_exporter.py), and (3F) validated read-only gcloud allow-list bridge (tools/gcloud_bridge.py).
4. Plane 4 — Target Google Cloud Control-Plane Telemetry Plane: Read-only introspection with bounded thread pools and a short-lived in-memory cache across Cloud KMS & Cloud HSM v1 (key rings, CryptoKeys, enabled versions, key IAM bindings, ImportJobs), Cloud Asset Inventory v1 searchAllResources (key-ring discovery, workloads with CMEK references, SSL policies and HTTPS/SSL target proxies, SSL and Certificate Manager certificates, Private CA authorities) and validated read-only gcloud describe/list lookups.
5. Plane 5 — Multi-Tenant Transactional PostgreSQL Persistence, Calibration Ledger & Object Storage Plane: Persists all authoritative transactional state in Cloud SQL for PostgreSQL (ADK DatabaseSessionService over postgresql+asyncpg plus DistributedAuthStore over postgresql+psycopg, managed by Alembic migrations in migrations/): conversation history and per-turn "Answered by" telemetry (sessions, events, pqc_session_metadata), corporate user profiles (pqc_tenant_users), server-side session revocation and PKCE state (pqc_auth_sessions, pqc_oauth_transactions, pqc_consumed_nonces), non-secret GCP connection configs (pqc_user_connections), Cloud KMS envelope-encrypted delegated credentials (pqc_delegated_credentials via pqc_agent/credential_service.py), and Mosca calibration events (pqc_calibration_events). Cloud Storage (GcsArtifactService via PQC_ARTIFACT_BUCKET) is reserved exclusively for uploaded session artifacts (gs://<ARTIFACT-GCS-BUCKET>/pqc_agent/<user_id>/) and exported Markdown/HTML reports (never mounted via GCS FUSE for transactional database files); the CycloneDX v1.6 CBOM JSON is returned by export_cyclonedx_cbom.

## 4. Stakeholder Calibration Ledger & Mosca Parameter Architecture

A core architectural differentiator of this AI system is that Mosca's inequality is evaluated with the customer's own stakeholder inputs, recorded per scope in an auditable ledger, instead of hidden defaults:

1. Phase 1 — Structured Context Ingestion: During stakeholder interviews (guided by Agentic PQC Discovery Questionnaire), the consultant executes Calibration Prompts (cataloged in Part III of this Guide) or uploads the completed questionnaire. The agent invokes calibrate_assessment_context only for values the stakeholders or the document actually state, recording the scope, sector, data shelf-life (X), migration time (Y), CRQC threat horizon (Z), API gateway header limit and the source of each value (provided vs. sector baseline default) in the transactional PostgreSQL calibration table (pqc_calibration_events).
2. Phase 2 — Scope-Keyed Calibration Retrieval: When quantum risk is assessed, the quantum_risk_agent calls get_historical_calibration_profile(scope), which returns only the calibration recorded for that exact scope (CALIBRATED_FOR_SCOPE) or, if none exists, the labeled ENTERPRISE_DEFAULT baseline (DEFAULT_BASELINE_NOT_CALIBRATED). Prior stakeholder inputs are reused without re-prompting and never leak across scopes.
3. Phase 3 — Transparent Mosca Evaluation: The tool returns the Mosca arithmetic (X + Y, Z and the safety margin M = Z - (X + Y)) and whether X + Y > Z holds; on a default baseline the agent states that the parameters are not calibrated and lists the questions needed to validate X, Y and Z. The recorded gateway header limit informs remediation sequencing (for example, raising header limits before switching to larger ML-DSA signatures), and Tier-0 projects can be calibrated as their own scopes. No financial figures are computed.

### 5.2 AI Safety, Anti-Hallucination & STRIDE Threat Mitigation Controls

- Mitigating LLM Arithmetic & Scoring Hallucinations (Integrity): Scorecard KPIs are computed by compute_pqc_scorecard with deterministic, reproducible arithmetic; every KPI carries value, numerator, denominator and definition (four KMS KPIs, a weighted KMS maturity index and optional TLS 1.3 and BYOK import-job KPIs). The agents must use these numbers exactly as computed, always with numerator and denominator, and never present their own conclusions as tool output.
- Data Provenance & Model Transparency (Non-Repudiation): Every evidence payload carries a data_source label (LIVE_GCP_API vs. SIMULATED_DEMO_DATASET) and a timestamp. Demo data is returned only when explicitly requested (PQC_SIMULATION_MODE=TRUE or an explicit demo scope; PQC_SIMULATION_MODE=FALSE in production), is never a silent fallback for API errors and carries a simulation_notice. Every answer shows "Answered by" (served_by): the real Vertex AI model_version, number of LLM calls, tokens and the agents that took part, persisted in the conversation history.
- Multi-Tenant User & Sandbox Isolation (Confidentiality): Every request is authenticated via verified Cloud IAP JWT (X-Goog-IAP-JWT-Assertion) or signed HttpOnly session cookie (pqc_agent/auth_guard.py + pqc_auth_sessions) and bound via ContextVar (bind_user_id + set_current_tenant_user) to the user's isolated PostgreSQL records (pqc_session_metadata, pqc_user_connections), Cloud Storage artifact prefix, and Cloud KMS AES-256-GCM envelope-encrypted delegated credentials (pqc_agent/credential_service.py), rejecting cross-user user_id access with HTTP 403. Runtime scope resolution (_resolve_scope) also redirects an internal Vertex AI tenant-project scope (-tp suffix) to the configured organization scope, so tenant projects are never scanned.
- Prompt Injection & Tool-Argument Sanitization (Tampering): Scope identifiers are normalized before calling Google Cloud client libraries and calibration parameters are type-checked. execute_gcloud_command runs only validated read-only gcloud commands (allow-listed verbs such as list, describe and get-iam-policy); mutating verbs, key-usage operations (encrypt, decrypt, sign, decapsulate) and shell metacharacters are blocked.

## 6. Non-Functional Requirements: Scalability, Resilience, Observability & FinOps

- High-Concurrency Throughput & Latency: Raw evidence collection runs in parallel with bounded thread pools (up to 8 workers for KMS key inspection, up to 16 for import-job key rings), paginated Cloud Asset Inventory searches and a short-lived in-memory cache (PQC_SCAN_CACHE_TTL_SECONDS, default 300 s) so specialist agents re-read the same evidence without repeating API calls. End-to-end time is dominated by Gemini reasoning and grows with inventory size and the number of agents involved; no fixed latency is promised.
- Graceful Degradation & Explicit Errors: Implements per-target exception isolation: if an API is disabled or a permission is missing in one project or location, the error is recorded in collection_errors (with the missing role or API) without aborting the rest of the scan, and the agents report every gap explicitly. Model failures are never masked: /api/chat returns HTTP 502 with the error and no templated report is substituted.
- Vertex AI Token FinOps & Context Efficiency: Tool outputs are serialized as compact JSON (separators=(',', ':')) and cached briefly; the default thinking level is MEDIUM (Gemini 3 models use their default temperature, older models 0.2), and every answer reports prompt, output and thinking tokens in served_by, making token consumption visible per turn.

## Part II — L400 Technical Design Document (5 Specialist Agents, 13 ADK Tools, Quantum Estimates & CBOM)

## 1. Engineering Context, Breaking Changes & Deployment Configuration Template

Migrating enterprise cloud infrastructure to Post-Quantum Cryptography (PQC) under NIST FIPS 203 (ML-KEM), FIPS 204 (ML-DSA), FIPS 205 (SLH-DSA), NIST IR 8547 (Final, Oct 2026), White House EO 14412, and NSA CNSA 2.0 is not a drop-in key rotation. It introduces fundamental mathematical, wire-format, and API breaking changes that require evidence-based automated analysis:

- Harvest Now, Decrypt Later (HNDL) & Store Now, Decrypt Later (SNDL): Adversaries intercept encrypted TLS sessions, database backups, and archival ciphertexts today to decrypt them retroactively once Cryptographically Relevant Quantum Computers (CRQCs) reach the ~2,330 to ~4,098 logical qubit threshold required by Shor's algorithm.
- Wire-Format & Artifact Size Expansion (20x to 51x Bloat): Classical ECDSA P-256 signatures occupy 64 bytes (and RSA-2048 occupies 256 bytes), whereas NIST FIPS 204 ML-DSA-65 signatures require 3,309 bytes (~4.4 KB in Base64URL JWTs) and public keys require 1,952 bytes. This breaks reverse proxies, NGINX/Envoy ingresses, Apigee API Gateways, and browser cookies configured with 4KB/8KB HTTP header limits, as well as fixed-width database columns (e.g., VARBINARY(256)).
- Cryptographic API Contract Shift (Decrypt -> KEM Encapsulate/Decapsulate): Post-quantum key establishment (ML-KEM / X-Wing) eliminates direct asymmetric decryption (AsymmetricDecrypt). Applications must be refactored to execute client-side Key Encapsulation (Encapsulate) paired with Cloud KMS Decapsulate() and RFC 9180 Hybrid Public Key Encryption (HPKE) or Google Tink SDK envelope encryption.
- Digital Signature Pre-Hashing Shift (Digest -> Raw Data / External-Mu): Classical Cloud KMS AsymmetricSign accepts pre-computed SHA-256/384 digests, whereas ML-DSA (FIPS 204) requires signing the raw message payload (data field) or computing a 64-byte external-mu hash over the public key TR and message.

## 3. Deep Specification of the 4-Layer Evidence Collection & Evidence-Level Correlation Model

### 3.1 Intelligent Runtime Scope Resolution & Tenant Sandbox Interception (_resolve_scope)

When executed inside managed Vertex AI Agent Engine containers (optional deployment path), the runtime can expose internal Google-managed tenant project identifiers (for example names ending in -tp). The _resolve_scope(target) function in tools/gcp_inventory.py normalizes the requested scope (organizations/<id>, folders/<id>, projects/<id> or a bare project ID), redirects internal tenant projects to the configured organization (GCP_ORGANIZATION_ID), and passes organization and folder scopes directly to Cloud Asset Inventory, which discovers KMS key rings and workloads across all child projects. The coordinator is also instructed never to pass -tp projects as scope.

### 3.2 Layer 1 — Cloud KMS, Cloud HSM & Cloud EKM Control-Plane Introspection

- API Traversal Pattern: Discovers key rings through Cloud Asset Inventory, then iterates concurrently across projects/*/locations/*/keyRings/*/cryptoKeys via cloudkms.googleapis.com/v1, reading the version template, the primary and every enabled CryptoKeyVersion (the weakest algorithm among them is reported as the effective algorithm) and the key's IAM bindings.
- Extracted Metadata Attributes: Captures purpose (ENCRYPT_DECRYPT, ASYMMETRIC_SIGN, ASYMMETRIC_DECRYPT, MAC, KEY_ENCAPSULATION), protectionLevel (SOFTWARE, HSM, EXTERNAL, EXTERNAL_VPC), algorithm (e.g., RSA_SIGN_PSS_2048_SHA256, EC_SIGN_P256_SHA256, GOOGLE_SYMMETRIC_ENCRYPTION, PQ_SIGN_ML_DSA_65, KEM_XWING), rotationPeriod, nextRotationTime, labels and IAM bindings, plus factual classification (quantum_status, threat model, NIST reference, artifact sizes and Cloud KMS post-quantum alternatives). Unknown algorithms are classified UNKNOWN_REQUIRES_REVIEW (fail-closed), never as safe.
- Zero-Key-Material Guarantee: The scanner never invokes AsymmetricDecrypt, AsymmetricSign, Decapsulate, or Secret Manager accessSecretVersion. Only control-plane configuration descriptors are read.

### 3.3 Layer 2 — Evidence-Level Workload Correlation (correlation_analyst_agent)

To determine which applications are affected when a classical KMS key is migrated to PQC, the correlation_analyst_agent (Gemini) reasons over evidence from collect_kms_inventory and collect_workload_evidence (Cloud Asset Inventory, cloudasset.googleapis.com/v1) and assigns exactly one evidence level per key-to-workload link; there is no hardcoded workload catalog or heuristic correlation in code:

1. STRONG — Exact CMEK Reference (Cloud Asset Inventory searchAllResources kmsKey): The workload resource (Cloud Run, GKE, Compute Engine instances and disks, Cloud Storage, BigQuery, Cloud SQL, Secret Manager, Pub/Sub, Artifact Registry) references the exact Cloud KMS key (cmek_references). CMEK keys are symmetric (AES-256-GCM), so the migration impact is usually limited to rotation hygiene; the agent states the impact per workload.
2. MEDIUM — IAM Binding + Verified Service Account: The key's IAM bindings grant a cryptographic role (e.g., roles/cloudkms.cryptoKeyEncrypterDecrypter, roles/cloudkms.signerVerifier or roles/cloudkms.cryptoKeyDecrypter) to a service account AND a read-only gcloud describe (execute_gcloud_command) confirms that the workload runs as that service account. This is the main path for asymmetric keys, which have no CMEK references.
3. WEAK — Naming or Label Similarity Only: The key and the workload share only naming or label similarity. WEAK links are flagged as hypotheses to validate with the application owner and are never presented as facts.
4. Consumer Not Identified & Migration Impact: Keys without an identified consumer are listed explicitly as "consumer not identified", with the missing evidence. For each correlated key the agent explains the application impact of migrating it (API contract, ciphertext or signature size growth, client library and verifier compatibility, stored ciphertexts, HTTP header limits) and emits a validated_correlations JSON list that feeds the CycloneDX CBOM.

### 3.4 Layer 3 & 4 — Network Edge TLS Policy & BYOK ImportJob Evidence Collectors

- Network Edge TLS Policy Collector (collect_tls_policies): Reads SSL policies and HTTPS/SSL target proxies from Cloud Asset Inventory (querying the Compute Engine SslPolicies API when CAI omits postQuantumKeyExchange) and reports, per proxy, the effective policy (a proxy without an attached policy uses the Google Cloud default: COMPATIBLE profile, minimum TLS 1.0, postQuantumKeyExchange DEFAULT), its minimum TLS version, profile, post_quantum_key_exchange mode (ENABLED, DEFAULT or DEFERRED) and custom features. Hybrid post-quantum key exchange (X25519MLKEM768, frontend TLS 1.3 clients only) is enabled by default starting October 2026 unless postQuantumKeyExchange is set to DEFERRED; policies set to DEFERRED (which disallows X25519MLKEM768 until October 2027) and clients limited to classical handshakes remain harvest-now-decrypt-later exposure.
- BYOK Import-Job Collector (collect_kms_import_jobs): Queries projects.locations.keyRings.importJobs.list for key rings discovered through Cloud Asset Inventory and reports each ImportJob's import method, wrapping family and transport_quantum_status: classical RSA-OAEP wrapping (e.g., RSA-OAEP-3072-SHA256) vs. post-quantum HPKE wrapping (X-Wing, ML-KEM-768, ML-KEM-1024). The remediation_architect_agent, not the tool, proposes the migration of classical BYOK wrapping.

## 4. Quantum Resource Estimates (Literature, with Citations) & Illustrative CRQC Scenario Model

### 4.1 Why ECDSA P-256 & P-384 Need Fewer Logical Qubits Than RSA-2048

Classical security intuition assumes ECDSA P-256 (128-bit classical security) is stronger than RSA-2048 (112-bit classical security). However, under Shor's algorithm on a fault-tolerant quantum computer, the required number of logical qubits scales linearly with key bit-length n: Q-logical(RSA) = 2n + 2 = 4,098 for n=2048 (Häner, Roetteler & Svore, 2017), whereas Q-logical(ECDLP) = 9n + 2*ceil(log2(n)) + 10 = 2,330 for n=256 (Roetteler et al., 2017). Elliptic-curve keys therefore need fewer logical qubits than RSA-2048 under these constructions, but other constructions trade qubits for gates and time, so the tool reports the break order as uncertain. The quantum_risk_agent prioritizes with explicit reasoning (harvest-now-decrypt-later exposure of decryption and key-establishment keys, forgery risk of long-lived signing keys and trust anchors) rather than a fixed rank table.

### 4.2 Illustrative CRQC Scenario Model (Not a Forecast) & Optional Business-Impact Sizing

1. Illustrative Logical-Qubit Growth Scenarios: Samples 10,000 seeded trajectories (seed 42, 2026-2035) of logical-qubit growth: a log-normal starting point (median 140 logical qubits in 2026), normally distributed annual growth (mean 0.55, standard deviation 0.11) and an optional breakthrough multiplier (1.35x-1.85x). All assumptions are returned with the results; the model is explicitly illustrative and NOT a forecast of when a CRQC will exist.
2. Annual Curve Output: For each year, reports the median and 95th-percentile logical qubits and the share of scenarios reaching the published logical-qubit thresholds for ECC P-256 (2,330), ECC P-384 (3,484), RSA-2048 (4,098) and RSA-4096 (8,194). Mosca's inequality is evaluated separately with the stakeholder-calibrated (or labeled default) X, Y and Z from the calibration ledger (Section 5).
3. Business Impact (Optional, Customer Inputs Only): The tools produce no financial figures and the agents never invent dollar amounts. Business impact is sized only with the customer's own inputs (data volumes and classification, incident and breach-cost history, cyber-insurance limits or BIA, applicable fines such as LGPD/GDPR) and presented as ranges with visible assumptions. Q-VaR (FAIR-style: loss-event frequency x loss magnitude, expected loss and loss-exceedance) is an optional analysis performed with the consultants, never computed automatically by the agent.

## 5. Mosca Calibration Ledger Design (tools/calibration_engine.py)

To evaluate Mosca's inequality with each customer's own inputs instead of hidden defaults, without manual code edits, tools/calibration_engine.py implements a persistent, scope-keyed calibration ledger:

- Longitudinal Calibration Ledger (pqc_calibration_events): Every call to calibrate_assessment_context inserts a timestamped transactional record in PostgreSQL containing scope, user_id, tenant_domain, industry_sector and sector_label, the Mosca arithmetic (X, Y, X + Y, Z, margin Z - (X + Y) and whether X + Y > Z), gateway_header_limit_kb, parameter_sources (provided vs. sector_baseline_default per value) and parameter_source_note.
- Default Sector Baselines (Assumptions to Validate): BFSI_BANKING (X=15y, Y=3y, Z=8.5y), HEALTHCARE_GENOMICS (X=35y, Y=5y, Z=8.5y), PUBLIC_SECTOR_DEFENSE (X=30y, Y=4y, Z=7.5y), TELECOM_5G_CLOUD (X=10y, Y=3y, Z=8.5y), ENERGY_OT_INDUSTRIAL (X=12y, Y=7y, Z=8.5y) and ENTERPRISE_DEFAULT (X=10y, Y=2y, Z=8.5y). They are default assumptions, used only for values the stakeholders did not provide, always reported as such, and carry no financial multipliers.
- Scope-Keyed Retrieval: The quantum_risk_agent calls get_historical_calibration_profile(scope), which returns the latest record and recent trail for that exact scope (CALIBRATED_FOR_SCOPE) or the labeled ENTERPRISE_DEFAULT baseline (DEFAULT_BASELINE_NOT_CALIBRATED); in the latter case the agent says the parameters are not calibrated and lists the questions needed to validate X, Y and Z. Recorded values persist across turns and sessions and never leak across scopes.

## 6. Deterministic Scorecard Equations, CycloneDX v1.6 Schema & Refactoring Blueprints

### 6.1 Separation of Asymmetric and Symmetric Denominators (Auditable-Arithmetic Guardrail)

To prevent LLMs from conflating symmetric AES-256 keys with asymmetric RSA/ECC keys, compute_pqc_scorecard (via compute_scorecard_from_keys) computes every KPI with explicit value_pct, numerator, denominator and definition: (1) asymmetric_pqc_migration = active asymmetric keys using a post-quantum algorithm / all active asymmetric keys; (2) symmetric_quantum_resistance = active symmetric/MAC keys with >= 128-bit post-quantum security / all active symmetric/MAC keys; (3) symmetric_rotation_hygiene = active ENCRYPT_DECRYPT symmetric keys with automatic rotation <= 90 days / all active ENCRYPT_DECRYPT symmetric keys; (4) algorithmic_quantum_safe = active keys whose algorithm is post-quantum or quantum-resistant / all active keys; (5) weighted_kms_pqc_maturity = weighted average of (1)-(3) (60% / 25% / 15%, renormalized over the KPIs that apply in the scope); and, when include_network_and_byok is true, (6) https_proxies_requiring_tls_1_3 = target proxies whose effective SSL policy requires TLS 1.3 / all target proxies and (7) byok_import_jobs_using_pqc_wrapping = active import jobs using post-quantum HPKE wrapping / all active import jobs. A zero denominator is reported as not applicable instead of a number.

## 5. Part 4 — How Stakeholder Calibration & the Scope-Keyed Ledger Work

The Agentic PQC Readiness & CBOM Engine does not retrain or self-learn; it reuses the stakeholder inputs recorded for each scope (implemented in tools/calibration_engine.py and enforced by the agent instructions in pqc_agent/agent.py):

- 1. Persistent Longitudinal Memory (pqc_calibration_events): When a consultant or customer engineer states a Mosca parameter or gateway limit, in the chat or in an uploaded document (such as adjusting X from 10 to 25 years for biometric data or noting an 8KB Apigee header limit), the agent invokes calibrate_assessment_context to insert a structured transactional event into the PostgreSQL calibration ledger. Values are recorded only when actually stated.
- 2. Scope-Keyed Recall (No Re-Prompting Required): Per its instructions, the quantum_risk_agent calls get_historical_calibration_profile(scope) when it assesses risk. The tool returns the most recent record for that exact scope (Mosca X, Y, Z, gateway limit and parameter sources) or the labeled default baseline; the agent applies the recorded values and states clearly when the parameters are not calibrated.
- 3. Progressive Refinement Across Engagement Phases: In Week 1 (Mobilization), Mosca uses the labeled sector baseline (e.g., BFSI_BANKING: X=15y, Y=3y, Z=8.5y), reported as not calibrated. In Week 2 (Agent-Assisted 4-Vector GCP Discovery), as application and PKI owners provide data shelf-life, gateway limits and project tiers via Calibration Prompts 1–4, the agents' risk prioritization and per-key remediation plans use the recorded values on the next run. Business impact is sized only with the customer's own inputs.
- 4. Multi-Customer Isolation & Ledger Separation: Each calibration entry is keyed by scope (organizations/<CUSTOMER-ORG-ID>) and tenant_domain, and get_historical_calibration_profile never returns another scope's values. In customer enclaves, each customer engagement runs on its own isolated Cloud SQL PostgreSQL database.
