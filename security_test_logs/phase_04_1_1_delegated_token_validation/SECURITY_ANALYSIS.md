## 1. Root Cause & Findings Classification

Investigation of the complete 9-step delegated access-token workflow (`pqc_agent/workspace_server.py`, `pqc_agent/credential_service.py`, `tools/gcloud_bridge.py`, `tools/gcp_inventory.py`, `tools/pqc_detectors.py`, and `main.py`) found **both a legitimate workflow compatibility break and five concrete security defects**:

### B. Legitimate Delegated-Token Compatibility Defect Remediated

- **Missing Server-Bound Auto-Resolution (`tools/gcloud_bridge.py`, `pqc_agent/workspace_server.py`, `tools/gcp_inventory.py`):**
  - Previously, when an operator onboarded a tenant via `PQC_ALLOWED_PROJECTS`, `PQC_ALLOWED_ORGANIZATIONS`, or `PQC_TENANT_SCOPE_POLICY`, non-admin sign-in (`POST /api/auth/google` with `use_token_for_gcp_connection=True`, `GET /api/auth/oauth/callback`, or `POST /api/auth/tool-consent`) persisted `organization_id=""` and `project_id=""`.
  - Downstream `/api/sessions` built malformed `organizations/`, `/api/chat` defaulted to hardcoded `organizations/31564119954`, and `_resolve_scope("default")` substituted `DEFAULT_ORGANIZATION_ID`, causing legitimate delegated scans to fail with `UNAUTHORIZED_RESOURCE_SCOPE`.
  - **Fix:** Added `resolve_server_bound_defaults(uid)` so unambiguous single-scope server policies automatically populate `organization_id`/`project_id`/`active_scope_uri` on connection defaults, connection reads, token bindings, session creation, chat turns, and symbolic `_resolve_scope()` calls — strictly server-side with zero client override ability.

## 2. Security Invariants Enforced

1. **Server-Side Scope Authority:** `PQC_TENANT_SCOPE_POLICY`, `PQC_ALLOWED_ORGANIZATIONS`, `PQC_ALLOWED_PROJECTS`, and `PQC_ALLOWED_FOLDERS` are authoritative across all scope dimensions simultaneously.
2. **No Client Scope Manipulation:** Client-supplied `scope`, `project_id`, `organization_id`, or `target_scope` payloads cannot override a server-bound scope, cannot bind arbitrary scopes in production without server policy, and cannot mutate/pivot an already-established tenant scope.
3. **Fail-Closed Missing Scope:** Delegated tokens without an authorized org/project/folder fail closed with `UNAUTHORIZED_RESOURCE_SCOPE (MISSING_AUTHORIZED_SCOPE)` and actionable onboarding guidance.
4. **Zero Unauthorized SDK Calls & Zero Ambient ADC Fallback:** `authorize_gcp_scope()` and delegated token validation (`load_delegated_token()` + expiry/syntax checks) execute before `_SCAN_CACHE` reads and before instantiating `AssetServiceClient`, `KeyManagementServiceClient`, `SslPoliciesClient`, or `RegionSslPoliciesClient`. `google.auth.default()` is never called for delegated-token users.
5. **Immediate Scope & Token Revocation:** Changes to server scope policies or credential expiration/revocation take effect immediately, invalidating cached inventory reads across all 5 collectors and HTTP endpoints.
6. **Preserved Admin ADC & Demo Modes:** `PQC_ADMIN_EMAILS` deny-by-default ADC allowlisting and explicit demo/simulation modes (`demo-pqc-project`, `PQC_SIMULATION_MODE=TRUE`) remain intact.

## 3. Required Production Onboarding Contract

Because a valid Google OAuth 2.0 access token **does not** establish which GCP organization, folder, or project a tenant is permitted to scan inside this multi-tenant application, production Cloud Run deployments **must** explicitly bind each tenant (or corporate domain) server-side via one or more of:

- `PQC_TENANT_SCOPE_POLICY` (recommended JSON mapping principals or `@domain` rules to explicit `organizations`, `projects`, and `folders` lists),
- `PQC_ALLOWED_ORGANIZATIONS` (e.g., `alice@corp.example=111111111111`),
- `PQC_ALLOWED_PROJECTS` (e.g., `alice@corp.example=tenant-a-proj-01`),
- `PQC_ALLOWED_FOLDERS` (default-deny unless explicitly configured).

Without server-side scope policy in production, non-admin delegated-token tenants intentionally fail closed (`MISSING_AUTHORIZED_SCOPE`) rather than permitting client-driven scope self-binding.

## 4. Remaining Limitations & Production-Safety Assessment

### Remaining Limitations
1. **No Live GCP / Cloud SQL / Vertex AI Execution in Phase 4.1.1:** All tests in this task run against mocked identity providers, mocked Google Cloud SDK clients, and isolated local SQLite databases (per Section 4 & Section 6 restrictions).
2. **Multi-Scope Tenant UX Selection:** When a server policy grants a tenant *multiple* organizations or *multiple* projects (`len > 1`), `resolve_server_bound_defaults()` leaves `active_scope_uri=""` to avoid guessing; the tenant must explicitly choose one of their server-allowlisted scopes in `/api/connection`, `/api/chat`, or `/api/sessions` (any non-allowlisted scope is rejected with HTTP 403).
3. **Non-Production Local Initial Binding Compatibility:** To preserve backward compatibility with existing Phase 3 local unit tests that run without `K_SERVICE` and without `PQC_ALLOWED_*` env vars, a brand-new non-admin connection with empty scope in local non-production mode may establish its initial scope once via `POST /api/connection`, after which subsequent re-binding or pivoting to a different scope is denied (HTTP 403). In production (`K_SERVICE` / `PQC_PRODUCTION_MODE=true` / `PQC_ENV=production`), initial self-binding is also strictly denied.
4. **Child Project Listing Under an Authorized Organization:** When a tenant is explicitly authorized for `organizations/<id>`, CAI discovers child KMS key rings within that organization and KMS reads them under the tenant's delegated token (enforced by GCP IAM); no secondary per-project application allowlist is layered on top of org-level child reads.
5. **No Automated CI Workflows:** The repository has no `.github/workflows` CI pipeline at this revision; all recorded test counts come from local workstation runs.

### Production-Safety Assessment
- **Architecture & Code-Level Assessment:** The remediated delegated-token flow enforces fail-closed server-side scope binding, blocks partial-policy and client-payload scope overrides, prevents expired/invalid tokens from constructing SDK clients, and preserves strict tenant isolation.
- **Production Readiness Caveat:** **Do NOT treat mocked unit/API tests alone as proof of live production readiness.** Before enabling delegated-token scanning in production Cloud Run, operators must validate end-to-end against real Google OAuth 2.0 PKCE, Cloud SQL PostgreSQL, Cloud KMS envelope encryption (`PQC_KMS_KEY_NAME`), real `PQC_TENANT_SCOPE_POLICY` configuration, and live Cloud Asset Inventory / Cloud KMS IAM permissions in a non-production staging environment.
